# 리시버 설계 의도 (RECEIVER_DESIGN)

Copyright 2026 SEIZIA (Jaeyoung Ko). SPDX-License-Identifier: Apache-2.0

이 문서는 `brv` 리시버의 **설계 의도**의 진실이다. [CLAUDE.md](../CLAUDE.md)의 "리시버 설계 원칙"은
이 문서의 요약이고, 근거·이력·미확정 사항은 여기에 있다. 코드가 이 문서와 어긋나면 코드를
기준으로 문서를 고치지 않는다 — 문서를 먼저 고치거나(변경 규약 참조) 코드를 문서에 맞춘다.

확정일: 2026-09-09. 발단: brv 0.6.39 검토(다중 바인딩 머신의 대화형 세션 MCP 기동 불가,
러너 지원 표기 불일치, 데몬 슬롯 다툼)와 같은 날의 실측(설치기 재실행이 라이브 세션을 밀어냄,
갱신 뒤 러너가 살려 둔 0.6.36 세션 어댑터가 옛 코드로 서버에 JOIN, `brv status`가 슬롯을 빼앗음).
결정은 [brevduva-server/PLAN.md 8장](../../brevduva-server/PLAN.md) 2026-09-09 항목에도 기록했다.

## 1. 한 문장

**리시버는 OS 서비스 하나다. 서버 채널 슬롯은 리시버만 쥐고, 세션·CLI·GUI 어댑터는 전부
리시버에 로컬로 붙는 손님이다. 리시버는 받은 메시지를 수신처 바인딩에 붙은 유인 세션에 밀어
넣고, 붙은 세션이 없으면 무인으로 깨운다.**

## 2. 확정 원칙

번호는 CLAUDE.md의 원칙 번호와 같다. 각 항목은 "원칙 — 근거 — 현재 코드(0.6.39)와의 차이" 순이다.

### P1. 리시버는 OS 서비스로 상주한다

- Windows = SCM 서비스(LocalSystem, 깨우기는 로그온 사용자 명의), Linux = systemd 사용자 유닛 +
  linger, macOS = launchd. 포그라운드 `brv daemon`은 개발용이며 제품 경로가 아니다.
- 근거: "자리 비운 사이에도 에이전트끼리 일한다"가 서비스의 핵심 가치(2026-08-29 업무시간 정책
  기각, 2026-09-03 LocalSystem 결정).
- 현재: 세 OS 모두 `brv daemon install`이 있다. 남은 차이는 온보딩이 서비스를 선택 사항으로 두는
  것(`--attended-only`, 비대화형 기본값 "안 켠다")과 macOS LaunchAgent가 로그인 후 기동인 것.

### P2. 서버 채널 슬롯은 리시버만 쥔다

- 세션 어댑터(`brv mcp`), CLI 명령(`brv status` 등), GUI 어댑터(`connection worker`)는 서버에
  JOIN하지 않는다. 서버에 JOIN하는 코드 경로는 리시버 서비스 안에만 존재한다.
- 근거: 지금은 넷이 저마다 JOIN해 서로 자리를 뺏는다. 2026-09-08 로그의 standby 반복, 설치기
  재기동 뒤 라이브 세션 밀어내기, `brv status` 실행 금지 메모가 전부 이 하나의 원인이다.
  단일 활성 수신 세션(PROTOCOL 2.2, 2026-09-08 결정)은 유지하되 그 세션이 항상 리시버다.
- 구현(2026-09-09): `brv mcp`는 서버에 JOIN하지 않는다 — `local_plane/bridge.rs`로 로컬
  엔드포인트에만 붙는다. `brv status`도 리시버의 `/status`를 읽는다(종전에는 이 명령의 JOIN이
  데몬을 standby로 밀어냈다). **진행(2026-09-10~11)**: `brv send`는 리시버의 `/publish`로 보낸다(8단계).
  러너별 레거시 어댑터(`--claude-channel`·`--codex-cli-endpoint`·Desktop worker·`brv connect`)는 리시버
  소유 통로로 옮긴 뒤 삭제했다(7e). **완료(2026-09-11, 17단계)**: `brv listen`도 서버에 JOIN하지 않고 리시버의
  `/listen`만 읽는다 — 옛 JOIN 경로와 그것만 쓰던 도우미를 지웠고, CLI 진입점에 서버 수신 클라이언트를 여는 코드가
  남지 않았다. Claude Code Stop 훅(`brv hook stop`)은 JOIN하지 않는다(비파괴 peek) — 안내하는 `wait_for_message`는
  15단계로 평면에 다시 있다.

### P3. 세션은 리시버에 붙는다

- 러너(Claude Code, Codex, …)는 리시버가 여는 **로컬 HTTP MCP 엔드포인트**에 접속한다. 리시버가
  기동 시 러너 설정에 자기 URL을 등록한다(`brv mcp register`의 URL 판). HTTP MCP를 지원하지 않는
  러너에만 stdio 중계기가 남으며, 중계기는 파이프 전달만 하고 리시버 로직을 품지 않는다.
- 세션의 정체성(어느 바인딩인가)은 접속 시점에 정해진다 — URL 경로 또는 첫 호출의 `become`.
  이것으로 "다중 바인딩 머신에서 대화형 세션이 바인딩을 못 고른다"(0.6.39 검토 1번)는 사라진다.
- 로컬 통로는 Windows 명명 파이프 / macOS·Linux 유닉스 소켓 또는 localhost HTTP. 어느 쪽이든
  접속 토큰이 필요하다(같은 머신의 다른 사용자가 채널에 말하지 못하게). 방향(2026-09-09 U5,
  표준 관행 준수): 루프백에만 바인딩, 설치 시 생성한 무작위 토큰, 토큰 파일은 소유자만 읽기
  (유닉스 0600, Windows는 사용자 SID + SYSTEM + Administrators ACL — 현재 설정 폴더 권한과 동일),
  Windows 명명 파이프는 DACL로 같은 주체만 허용, HTTP는 MCP 스펙의 로컬 서버 요구(루프백·Origin
  헤더 검증으로 DNS 리바인딩 방지·인증)를 따른다. Docker·Jupyter·ssh-agent가 쓰는 모양이다.
  세부는 구현 시 검토한다.
- 근거: stdio MCP는 러너가 자식을 띄우는 규약이라 "리시버가 MCP를 띄워 둔다"는 불가능하다.
  러너가 우리에게 오게 하려면 HTTP뿐이다.
- 구현(2026-09-09): `local_plane/http.rs`가 루프백 MCP Streamable HTTP를 연다. `brv mcp`는
  얇은 stdio 브리지가 됐고 선택자(`--binding`)는 폐지됐다 — 0.6.39 검토 1번의 근본 수정이다
  (다중 바인딩 머신에서 세션이 그냥 붙는 것을 종단 시험이 검증한다). 브리지는 리시버와 버전을
  대조해 다르면 물러난다(P8). 깨어난 세션의 정체성은 `BREVDUVA_BINDING`·`BREVDUVA_WAKE`로
  브리지가 대신 세운다.

### P4. 붙음의 정의는 "메시지를 받을 수 있음"이다

- 러너의 입력 통로(Claude Monitor/Channels 알림, Codex app-server 큐 등)가 메시지를 실제로
  수락하면 붙은 것이다. 유휴 시간·프레즌스 추정·도구 호출 빈도로 붙음을 판단하지 않는다.
- "수락"은 "완료"가 아니다(기존 규약 유지). 수락 = 서버 ACK 시점, 완료 = 최종 reply/report.
- **받는 주체는 에이전트다 (2026-09-11 확정)**: 리시버는 전달자이므로 서버 확정(ACK)은 에이전트가 받았다는
  증거가 있을 때만 한다 — 모델의 receipt, 수동 수신 도구의 결과 반환, 깨운 세션의 `become(wake)`. 러너
  대기열 등록(queue id)·실행체 기동·리시버 기록 저장은 증거가 아니다. 넘기는 동안은 `WORKING`, 넘길 곳이
  없거나 결과 불명이면 `DEFER`로 서버에 알린다(PROTOCOL 7.2). 발단: 서버는 확인 없는 전달을 30초마다 다시
  보내고 실전달 5회를 넘으면 격리하는데, 7a~7d는 확인만 미뤄 긴 모델 턴·바쁜 작업·결과 불명에서 약 2.5분 뒤
  메시지가 격리될 수 있었다(시험이 서버 없이 돌아 드러나지 않음). "리시버가 기록한 뒤 확정"안은 전달자를
  수신자로 세는 것이라 기각했고, 같은 이유로 PROTOCOL 13.4의 영속 인계 계약(2026-09-07)을 폐지했다.
- **수동 수신도 받을 수 있음이다 (2026-09-11 확정)**: 입력 통로가 없는 세션이 `wait_for_message`·
  `wait_for_reply`로 기다리는 동안은 받을 수 있는 세션이다. 리시버가 밀어 넣을 수 있는 러너는 현재 Claude
  Code·Codex뿐이라, 그 밖의 호스트와 사람이 에이전트에게 백그라운드 감시를 시키는 경우를 위해 수동 수신을
  정식 모드로 둔다. 호출 사이 빈틈은 임대(90초 — 원격 MCP의 점유 임대와 같은 값)로 그 세션 몫을 붙들고
  (`WORKING`), 요청을 보낸 세션의 답은 무인 깨우기보다 그 세션을 먼저 기다린다. 한 번 대기의 상한은 45초다 —
  Codex 문서의 도구 호출 제한 60초·Claude Code HTTP 첫 응답 60초보다 짧게 두어, 호스트가 먼저 포기한 대기에
  넘겨 메시지를 잃지 않게 한다(2026-09-11 조사: Codex는 제한 초과 때 취소 알림을 보내지 않는 것으로 보인다).
  취소 알림(`notifications/cancelled`)이 오면 그 대기를 끝내고 넘기지 않는다.
  **구현(2026-09-11, 15단계)**: 라우터는 입력 통로 없는 홀더가 기다리는 중이거나 임대 안일 때, 또는 메시지가 그
  세션이 보낸 `request`의 반응일 때 그 세션 몫으로 붙들고(`WORKING`), 도구 결과로 돌려줄 때 기록(수락)·확정한다.
  붙든 몫의 기록은 받는 대기로 둔다 — 아직 에이전트에게 보이지 않았으므로 리시버가 재기동해 다시 넘겨도 결과
  불명이 아니다. 임대가 끝나거나(요청의 반응은 예외 — 세션이 바인딩을 쥐는 동안 붙든다) 세션이 바인딩을 놓으면
  `DEFER`로 되돌려 다음 전달은 무인 경로로 간다. 취소 알림에는 그 대기에 넘기지 않고 MCP 규약대로 응답하지 않는다 —
  이 알림이 닿으려면 중계기(`brv mcp`)가 요청을 동시에 넘겨야 해서, 한 줄씩 응답을 기다리던 중계기를 고쳤다. 입력
  통로가 붙은 세션은 이 도구를 거부한다(두 길 수신 금지). 한계: 호스트가 취소 알림 없이 대기를 버리면 그 대기가
  돌려준 메시지는 받는 이 없이 확정된다 — 상한 45초가 이 창을 좁힌다.
- **리시버 없는 환경도 1급이다 (2026-09-11 확정)**: 모바일·웹 Claude처럼 리시버를 설치할 수 없거나 설치가
  득이 없는 환경은 서버의 원격 MCP로 수동 수신한다. 리시버 설계는 이 경로를 깨지 않는다. 사람의 기기는 머신
  에이전트와 **별도 정체성**을 쓰도록 안내한다 — 같은 정체성이면 서버의 수신 자리 하나 규칙(PROTOCOL 2.2)에
  따라 리시버와 번갈아 가져가, 폰이 기다리던 답을 무인 깨우기가 가져갈 수 있다(2026-09-05 실측과 같은 구조).
  같은 정체성 공유는 "그 에이전트를 넘겨받기"라는 명시적 동작으로 보고, 로컬 작업 잠금과 서버 점유를 잇는
  프로토콜 확장은 수요가 확인될 때 한다.
  **점검(2026-09-11, 18단계)**: 실측으로 Claude Code(2.1.263)가 HTTP MCP 도구 호출의 첫 응답을 **60.0초**에 끊는 것을
  확인했다(로컬 느린 MCP 서버 — JSON 한 번 응답 50초 통과·75초는 60초에 연결 끊김). 서버 원격 MCP의 대기(종전 기본
  60초·최대 120초, JSON 한 번 응답)는 이 제한에 닿아 결과가 버려질 수 있었다 — 대기 한 번의 상한·기본을 서버 설정 45초로
  정정했다(PROTOCOL 12.2, 로컬 평면의 수동 수신과 같은 값). 헤더를 먼저 보내고 keep-alive를 흘리는 SSE 응답은 Claude
  Code의 첫 바이트 제한을 넘기지만(75·150초 실측 통과), Codex의 도구 호출 제한(기본 60초)은 풀지 못해 채택하지 않았다.
  Claude Code는 이와 별도로 응답·진행 알림 없는 HTTP MCP 호출을 300초에 끊는다(번들 코드 확인).
- GUI 앱에도 같은 정의를 적용한다(2026-09-09 U3 정리): MCP를 지원하는 GUI는 리시버의 HTTP MCP에
  붙어 send·reply를 할 수 있지만, MCP에는 서버가 모델의 턴을 시작시키는 표준 기능이 없다(알림은
  앱까지만 간다). 알림을 모델 입력으로 소비하는 호스트(Claude Code Channels, Codex Desktop 내부
  IPC)만 "받을 수 있음"이고, 그렇지 않은 GUI는 붙어 있어도 라우팅상 붙은 세션이 아니다 → P5의
  무인 경로. 별도 GUI 정책은 두지 않는다.
- 구현(2026-09-09): 밀어 넣은 메시지는 수락(receipt)이 있어야 서버에 ACK한다. `idle_park`는
  세션 쪽 용도가 **번복**됐다 — 세션이 서버 슬롯을 쥐지 않으므로 레거시 어댑터와 함께 사라졌다(7e).
  **정정(2026-09-11)**: 리시버(데몬) 자신도 `idle_park`를 쓴다. 깨운 세션의 완주를 기다리는 동안
  (`wait_wake`) 수신 루프가 받지 않아, 그 사이 온 메시지가 받는 쪽 버퍼에서 재전달 예산을 태우지 않게
  접속을 내려놓는 용도다. 세션 붙음 판정과 무관하므로 유지한다(9단계 범위 축소). **갱신(2026-09-11,
  14단계)**: 깨우기가 수신 루프를 막지 않게 되어 그 구간은 사라졌다 — 대기자 없이 메시지가 버퍼에 방치되는
  일에 대한 안전장치로만 남는다.
- **구현 정정(2026-09-10)**: 3단계 구현은 SSE 스트림이 열리면 곧 수신자로 표시했다. 이것은 P4를 넘어선
  판정이다 — 일반 MCP 호스트는 알림을 받아도 모델 턴을 열지 않으므로(U3), 통로만 연 세션에 밀어
  넣으면 수락이 오지 않는다. 그 세션이 붙어 있는 동안 메시지는 재전달만 반복되고 무인 깨우기로도
  가지 않는다 — U1이 막으려던 기아 상태다. 정정: SSE는 **제어 통로**(밀려남·종료 통지)로만 쓰고,
  수신자 판정은 **모델 턴을 여는 러너 입력 통로가 준비됐을 때만** 한다 — 리시버가 연 Monitor
  스트림이 붙었거나, 검증된 Codex 스레드가 등록됐거나, Channels 확인 사건이 수락된 세션일 때
  (RECEIVER_REBUILD_PLAN 7a·7c — Channels는 선언만으로는 부족하다: 클라이언트가 등록 여부를 알려 주지
  않기 때문이다). **정정 완료(2026-09-10)**: 등록부의 세션에 러너 입력 통로
  (`DeliveryTarget`)가 생겼고 그 통로가 실제로 붙어(`ready`) 있을 때만 수신자다. SSE는 제어 통지만
  싣는다. 회귀 시험이 "MCP 연결만으로는 수신자가 아니다"와 "붙기 전의 Monitor는 받지 않는다"를

### P5. 수신 라우팅: 붙은 유인 세션이 있으면 거기로, 없으면 무인 깨우기

- 리시버는 바인딩별로 "붙은 세션 등록부"를 가진다. 메시지가 오면 수신처 바인딩에 붙은 유인
  세션이 있으면 그 러너의 입력 통로로 밀어 넣는다. 없으면 기존 데몬 경로대로 무인으로 깨운다
  (`wake` 설정, 사전 점검 관문, 바인딩별 병렬 — 전부 유지).
- 무인으로 깨운 headless 세션도 그 바인딩에 "붙은 세션"이다(자기 자신이 등록부에 오른다).
- **붙은 세션이 없고 깨울 CLI 러너도 없으면 큐에 보관한다**(2026-09-09 U1 확정). 유인 세션이
  종료돼 통로가 사라진 경우는 "붙은 세션 없음"이므로 무인 경로다 — 사람이 다시 앉을 때까지 큐에만
  두면 기아 상태가 되기 때문. 기존 관문(러너 사전 점검 실패 시 채널에 붙지 않고 큐에 둠)이 그대로
  "CLI 없으면 큐 보관"이다.
- **받을 곳이 있을 때만 서버 자리를 잡는다 (2026-09-11 확정)**: 리시버는 바인딩에 깨울 러너가 있거나(사전
  점검 통과) 그 바인딩을 쥔 세션이 있을 때만 서버에 붙는다. 둘 다 없으면 붙지 않아 메시지가 전달 없이 서버
  큐에 남는다 — 온라인 표시가 정직하고(2026-09-03 결정 유지), 같은 정체성의 원격 수동 수신과 다투지 않는다.
  깨우기 설정이 없는 사용자도 리시버를 띄울 수 있어야 하므로 `[wake]` 없이 기동하고, `--attended-only`의 뜻은
  "서비스 없음"에서 "서비스는 설치하되 무인 깨우기는 끔"으로 바뀐다. 세션이 떨어진 뒤 곧바로 접속을 내리지
  않게 짧은 유예를 둔다.
  **구현(2026-09-11, 16단계)**: 바인딩을 깨울 수 있음 = 머신의 `[wake]`와 그 바인딩의 `wake_dir`이 둘 다 있음. 깨울
  수 있으면 종전 관문(사전 점검)을 통과할 때 붙고, 점검이 실패하는 동안에도 로컬 세션이 그 바인딩을 쥐면 붙는다 —
  그 세션이 보내고 받아야 하기 때문이다(이때 온 무인 몫은 30초 `DEFER`). 깨울 수 없으면 쥔 세션(수동으로 받는 세션
  포함)이 생길 때만 붙고, 받을 곳이 모두 사라지면 30초 유예 뒤 내려놓는다(상태 `dormant`). 운영 중 깨우기가 시작도
  못 하면 쥔 세션이 없을 때만 관문으로 돌아가고, 있으면 남아 무인 몫만 연기한다. 세션이 바인딩을 막 쥔 직후의 도구
  호출은 접속을 최대 10초 기다린다. `wake_dir` 없는 바인딩은 더 이상 "받을 수 없음"으로 건너뛰지 않는다. `brv init`의
  `--attended-only`(와 대화형 질문에 아니오)는 깨우기를 설정하지 않고 리시버 서비스를 등록한다 — 터미널 밖에서 플래그
  없이 실행되면 관리자 승인 창을 띄우지 않도록 등록하지 않고 안내만 한다.
- **무인 깨우기의 확정 시점 (2026-09-11 번복)**: 종전(2026-08-29)에는 스폰 성공 직후 ACK했다. 이제 스폰부터
  깨운 세션의 `become(wake)`까지 `WORKING`, `become` 때 ACK한다. `become` 없이 세션이 끝나면 `DEFER`로 되돌려
  다시 시도한다 — `become`을 못 한 세션은 채널 도구를 쓸 수 없어 답신을 못 보냈으므로 동료에게 중복 응답이
  가지 않는다. 한계: `edit`·`full` 권한 세션이 파일만 고치고 `become` 없이 끝나면 로컬 작업이 중복될 수 있다.
  **구현(2026-09-11, 14단계)**: 증거는 그 깨우기의 식별자로 한 `become`(브리지가 대신 세운 정체성 포함)과, 깨운
  프로세스가 CLI로 한 발행(`brv send`가 `BREVDUVA_WAKE`를 싣는다 — MCP를 쓰지 않는 깨우기 명령의 경로)이다.
  깨우기는 수신 루프를 막지 않는 별도 작업이다 — 종전처럼 루프가 세션 완주를 기다리면 그 사이 온 메시지는
  연기조차 못 해 격리될 수 있다. 바인딩당 깨우기는 여전히 하나이고, 진행 중에 새로 깨울 몫은 15초 `DEFER`한다.
  증거 없이 끝난 배치는 한 번만 되돌려 다시 깨운다. 두 번째도 증거가 없으면 확인하지 않은 채 둬 서버 격리로
  드러내고 발신자에게 실패를 알린다 — 증거를 낼 수 없는 깨우기 명령(brevduva 도구를 쓰지 않는 스크립트)이 같은
  일을 되풀이하지 않게 하는 상한이다. 착수 알림(`in-progress`)도 증거 때 낸다. JOIN에 `delivery` 조건이 없는
  서버(연장 수단 없음)에서는 긴 깨우기 중 격리되지 않게 종전처럼 스폰 직후 확정한다 — 호환 예외다.
- **`brv listen`은 리시버 관찰 명령이다 (2026-09-11 확정)**: 서버에 JOIN하던 옛 `listen`은 켜는 순간 수신
  자리를 빼앗고 받은 메시지를 소비해 에이전트에게 가지 않게 했다(P2 위반). 리시버의 로컬 엔드포인트에 붙어
  리시버가 받은 메시지와 그 행선지(세션 전달·깨우기·연기·결과 불명)를 보여 주고, 아무것도 가져가지 않는다.
  리시버가 없으면 그렇다고 말하고 끝난다 — 서버 직접 접속으로 대신하지 않는다.
  **구현(2026-09-11, 17단계)**: 평면의 관찰 흐름(구독자가 없으면 싣지 않음)에 받은 메시지 요약(본문 앞 200자)과
  행선지(`handed_to_session`·`held_for_manual_receive`·`unattended`·`deferred`·`consumed`), 수락(`receipt`·
  `manual_receive`), 결과 불명, 데몬의 깨우기 결과(`wake_started`·`wake_proven`·`wake_unproven`·`wake_failed`·연기)를
  싣는다. 로컬 엔드포인트의 운영자 표면 `GET /listen`(같은 자격)이 줄 단위 JSON으로 흘리고, `brv listen`은 그것을
  사람이 읽는 줄(또는 `--json`)로 보인다(`--binding`으로 거름). 느린 관찰자는 밀린 건수만 받고 라우팅은 기다리지 않는다.
- 구현(2026-09-09): `Plane::route`가 판단하고 `daemon.rs`의 수신 루프가 배치마다 부른다 —
  밀어넣기/큐 보관/무인 깨우기로 갈린다. 밀어 넣은 것은 ACK하지 않고 수락을 기다린다.
  **진행(2026-09-10, 7a)**: Claude Monitor 통로는 리시버 소유가 됐다. 리시버가 루프백 스트림을 열고,
  넘기기 **전에** 바인딩별 전달 기록(설정 디렉터리 `local-plane/<org>/<agent>/<channel>/`, 소유자 전용)에
  남기고, 세션당 한 번에 하나씩 넘긴 뒤 수락을 기다린다. 서버 확정은 수락 때 한다 — Monitor에는
  모델의 수락 말고 다른 수락 증거가 없기 때문이다. 수락 전에 통로나 세션이 사라지면 **결과 불명**으로
  남기고 자동으로 다시 넣지 않는다(모델이 이미 봤을 수 있다). 결과 불명은 같은 세션의 뒤늦은 수락이
  오면 관측 증거로 확정하고, 아니면 소유자가 `receiver_resolve`(received/retry, 확인 메모 필수)로 정한다.
  결과 불명은 **그 메시지만** 막고 바인딩 전체를 막지 않는다 — 다른 메시지는 다른 세션이나 무인
  깨우기로 가므로 대화 안 순서가 걸려 있지 않고, 바인딩 전체를 막으면 U1이 막으려던 기아가 된다.
  시스템 이벤트(`event`·`_` 발신자)는 모델 턴을 열지 않고 기록한 뒤 확정한다(기존 Channels 규약).
  **진행(2026-09-10, 7b)**: Codex CLI 작업 대기열 통로도 리시버 소유가 됐다. 세션이 자기 셸의
  `CODEX_THREAD_ID`를 넘기면 리시버가 쓰기 잠금으로 그 작업이 적재돼 있는지 확인하고(파일을 만들지 않는
  읽기), `codex queue`는 **사용자 명의 실행기**(윈도우 서비스는 winspawn, 그 외는 직접)로만 실행한다 —
  서비스 계정으로 Codex를 돌리는 코드 경로가 없다. 리시버는 사용자 프로필을 읽지 않으며, 작업의 프로필
  문맥(`codex_home`·실행 파일)은 사용자 명의로 도는 브리지가 자기 환경에서 채운다. 작업 id는 채우지
  않는다 — 모델이 자기 셸에서 읽는 기존 규약. 대기열 경로의 서버 확정 시점은 **queue id를 받은 때**다:
  작업의 대기열(`queue_1.sqlite`)이 영속 보관을 넘겨받는 러너 수준의 수락 증거이기 때문이다(Monitor는
  모델 수락이 유일한 증거라 수락 때 확정한다). 그래서 queue id를 받은 뒤 작업이 멈춰도 결과 불명이
  아니다 — 작업이 다시 적재되면 그 대기열에서 들어간다. **번복(2026-09-11, 14단계)**: queue id는
  러너가 넘겨받았다는 표지일 뿐 에이전트가 받았다는 증거가 아니다 — 서버 확정은 Monitor처럼 모델의 receipt 때
  하고, 그동안 `WORKING`으로 연장한다(P4 "받는 주체는 에이전트"). 넣지 못한 것이 확실하면(시작 실패·비정상 종료·
  제출 직전 작업 멈춤) 기록을 되돌려 서버 재전달 때 정상 경로를 타고, 들어갔는지 모르면(시간 초과·queue
  id 없음) 결과 불명으로 남긴다. 작업 적재 여부는 5초마다 다시 보고, 세션당 입력 통로는 하나다.
  **진행(2026-09-10, 7c)**: Claude Code Channels 통로도 리시버 소유가 됐다. Channels 서버는 stdio로만
  문서화돼 있어 브리지 경유이며, 알림 이름은 규격 그대로(`notifications/claude/channel`)다. 평면은
  Claude 호스트 세션의 initialize에 `experimental.claude/channel` 선언을 붙인다 — 채널 옵션 없이 시작한
  Claude는 무시하므로 무해하고, 선언만으로 수신자가 되지 않는다. Claude는 채널 등록 여부를 서버에 알려
  주지 않으므로(확인 응답·initialize 표시 없음) `receiver_connect(channels=true)`가 **확인 사건**을 한 번
  보내고, 모델이 그 사건의 receipt를 부르면 그때 통로가 준비된다 — 알림이 실제로 모델 턴을 열었다는
  관측 증거다. 사건 본문은 고정 안내이고 receipt 식별자는 속성(meta, 키는 영문·숫자·밑줄)에 싣는다.
  **동료 본문은 싣지 않는다** — Monitor·대기열과 같은 신뢰 경계로, 옛 세션 소유 Channels가 본문을
  사건에 실었던 것의 **변경**이다. 서버 확정은 Monitor처럼 모델 수락 때 한다. Claude CLI의 기본 통로는
  여전히 Monitor이고, Channels는 Claude를 `--dangerously-load-development-channels server:<등록 이름>`
  (또는 허용 목록의 플러그인 채널)으로 시작한 경우의 선택 통로다.
  **진행(2026-09-11, 7d)**: Codex Desktop 작업 통로도 리시버 소유가 됐다. 리시버(서비스)는 Desktop 내부
  IPC를 직접 열지 않고 **사용자 명의 도우미**(`brv desktop check`, 리시버 전용 `brv desktop submit`)를
  러너 입력과 같은 실행기로 띄운다 — 사용자 앱 안의 행동은 사용자 명의로(2026-09-03·09-10), 그리고 이
  명의는 옛 작업 연결(사용자 명의 worker)이 실기로 검증한 것과 같다. 작업 id는 모델이 자기 셸의
  `CODEX_THREAD_ID`를 넘기고(옛 connect 규약), 붙이기 전에 그 작업의 소유자가 외부 입력을 받는지
  확인한다. 전달마다 도우미가 소유자를 다시 확인하고 턴을 연다. 넣는 글은 Monitor와 같은 사건 한 줄을
  앱의 신뢰하지 않는 입력 칸에 싣고 **동료 본문은 싣지 않는다**(옛 worker가 봉투 전체를 실었던 것의
  **변경**). 서버 확정은 **모델 수락 때**다 — 턴이 열렸다는 것은 앱이 입력 칸을 받았다는 증거일 뿐
  모델이 읽었다는 증거가 아니어서, 대기열(queue id 때 확정)과 다르게 Monitor를 따른다. 턴 id는
  기록에 남겨 소유자가 결과 불명을 판단할 때 쓴다. 앱이 턴 처리 중이면(busy) 넣지 않은 것이 확실하므로
  같은 작업에 다시 시도하고(도우미가 45초까지 스스로 기다리고, 끝나면 리시버가 3초 뒤 다시 띄운다 —
  P6), 기다리는 동안 세션이 끝나면 결과 불명이 아니라 되돌린다. busy 외의 명시적 거절·보낸 뒤 끊김·
  시간 초과는 옛 경로대로 결과 불명이다. 소유자를 주기적으로 묻지 않는다 — 통로의 수명은 세션의
  수명이고, 제출 때 소유자가 없으면(넣지 않음 확실) 통로를 떼어 정상 경로로 돌린다. 옛 worker·
  `brv connect`·`desktop run`은 7e에서 삭제한다.

    위에 앱 서버를 프로세스 안에서 띄워 `thread/queue/add`를 부른다. 격리한 CODEX_HOME에서
    SQLite DB(queue·state·logs·memories·goals)·installation_id·skills·임시 git 등 파일 100여 개를
    만들고 스레드 조회 단계에서 멈췄다(인증 없이 그 단계까지 간다). ② CODEX_HOME·
    thread-writer-locks·잠금 파일의 ACL은 SYSTEM·Administrators·사용자에게 모든 권한(상속), Codex
    샌드박스 SID 380개에는 쓰기 거부. ③ `\\.\pipe\codex-ipc`의 DACL은 소유자=사용자, SYSTEM·
    Administrators·사용자 모든 권한, Everyone·ANONYMOUS 읽기. ④ LocalSystem으로 직접 실행하는 측정은
    관리자 권한이 없어 하지 못했다.
  - 판단: 접근 권한은 SYSTEM을 막지 않는다. 그러나 `codex queue`는 사용자 Codex 프로필 안에서 설정을
    읽고 파일을 만드는 실행체라, LocalSystem으로 돌리면 사용자 프로필에 SYSTEM 명의 파일과 SYSTEM
    환경 기준 동작이 섞인다. 2026-09-03 "리시버는 전달자이며 사용자 도구 안의 행동은 사용자 명의로"
    결정에 어긋난다. SYSTEM 직접 실행이 성공하더라도 이 결론은 바뀌지 않는다.
  - 파일을 만들지 않는 순수 통로(루프백 Monitor 스트림·SSE)는 서비스 프로세스가 직접 연다.
  - **회귀 수정(2026-09-10)**: 평면의 리시버 관리 도구(`receiver_status`·`receiver_doctor` 등)는
    `brv` CLI를 자식 프로세스로 실행한다. 평면이 서비스 안으로 들어오며 그 자식이 서비스 명의
    (Windows LocalSystem)로 돌게 됐었다 — SYSTEM 프로필의 설정을 보고 고치거나 사용자 설정 파일의
    소유자를 바꿀 수 있는 경로다. 관리 명령도 같은 사용자 명의 실행기로 돌린다(설정 프로필 고정,
    깨운 세션의 정체성 변수 제거, 상한 300초 — 넘기면 `timed_out`). 작업 셸 명령을 돌려주던 `connect`는
    7e에서 삭제됐다.
  - 소스 확인(openai/codex `rust-v0.153.4`): Windows의 `codex queue`는 항상 프로세스 안 앱 서버를
    쓰고, 두 프로세스가 공유하는 것은 CODEX_HOME의 `queue_1.sqlite` 하나다. 스레드를 적재한 프로세스가
    약 10초 주기로 그 DB를 읽어 유휴일 때 넣는다. 호출자 신원 검사는 없다. `CODEX_HOME` 없이 SYSTEM으로
    돌리면 SYSTEM 프로필의 다른 DB에 쓰여 사용자 세션에 닿지 않고, 지정하면 닿지만 사용자 폴더에 SYSTEM
    소유 파일이 생긴다. `thread-writer-locks/<id>.lock`을 쥔 프로세스가 곧 그 스레드를 적재한 세션이며,
    `queue`는 멈춘 스레드를 재개하지 않는다(메시지는 DB에 남아 재개 뒤 들어간다). macOS·Linux의 제어
    소켓은 0700 디렉터리 안 0600 파일이고 피어 자격 검사가 없어 같은 사용자여야 한다.
  - 전달 지연: queue 경로는 폴링 주기(약 10초)만큼 늦을 수 있다 — 수락 대기 창은 이보다 길어야 한다.
  - Desktop 내부 IPC(`codex-ipc`)는 비공개 Electron 코드라 소스로 확인할 수 없다. 서버 쪽 클라이언트
    신원 검사 여부는 7d 착수 전에 실측으로 확인한다.
    **정리(2026-09-11, 7d 착수 시)**: 이 머신에 Codex Desktop(26.903.9818.0)은 설치돼 있으나 실행 중이
    아니어서(프로세스·`\\.\pipe\codex-ipc` 없음) 실측하지 못했다. 대신 신원 검사 여부가 **설계에서 쟁점이
    아니게** 했다 — 서비스는 IPC를 열지 않고 사용자 명의 도우미만 연다. 도우미의 명의·요청 형식은 옛
    worker와 같아 실기로 검증된 범위다. 실제 앱에서 남는 검증(12단계): 신뢰하지 않는 입력 칸의 receipt
    안내를 모델이 따르는가, 서비스 모드 winspawn 도우미 실행.

### P6. 폴백 없음: 붙은 세션이 수락하지 않으면 큐에 남긴다

- 붙은 세션이 있는데 수락이 안 되면(러너가 턴 처리 중 등) 무인으로 넘기지 않는다. 메시지는
  서버 큐에 남고, 수락될 때 ACK한다. **정정(2026-09-11)**: "큐에 남긴다"는 확인만 미루는 것이 아니라
  `DEFER`로 서버 큐에 돌려놓는 것이다(PROTOCOL 7.2) — 확인만 미루면 재전달이 격리 판정 예산을 태워
  약 2.5분 뒤 격리된다.
- 근거: 같은 메시지가 유인·무인 두 세션에 이중 처리되는 것을 막는다. 서버 경유 store-and-forward
  (2026-08-25)가 큐의 진실이다.
- 경계(2026-09-09 U1 확정): "붙어 있지만 지금 못 받음"(러너가 턴 처리 중)은 이 원칙대로 큐 대기이고,
  "떨어짐"(통로 자체가 없음)은 붙은 세션이 없는 상태이므로 P5의 무인 경로다.

### P7. 한 세션은 여러 바인딩을 쥘 수 있고, 같은 바인딩은 최신 세션이 이긴다

- 로컬 세션 하나가 여러 `org/agent@channel` 정체성을 동시에 가질 수 있다. 송신 툴에 "어느
  바인딩으로"가 들어가고, 수신 알림에 "어느 바인딩으로 온 것인지"가 붙는다.
- 같은 바인딩을 다른 세션이 `become`하면 기존 세션은 밀려나고 **통지받는다**(그 세션의 해당
  바인딩 툴 호출은 "밀려남"으로 실패). 서버 쪽 JOIN 테이크오버(PROTOCOL 2.2)와 같은 규칙을
  리시버 로컬 등록부에 적용한다.
- **become hold**(2026-09-09 U2 확정, 같은 날 정의 확정): 작업 지시를 받아 처리 중인 세션은
  바인딩이 잠기고, 잠긴 동안 다른 세션의 `become`은 거부된다. 기본은 "최신이 이긴다"이고 hold는
  작업 중에만 성립하는 예외다. **DB 잠금과 같은 뜻**으로 정의한다:
  - 획득 = 세션이 회신을 요구하는 메시지(request)를 수락하는 순간(트랜잭션 시작).
  - 해제 = 그 작업의 **최종 reply 또는 최종 report(failed 포함)가 서버에 확정되는 순간**(커밋).
    진행 보고(in-progress)는 해제하지 않는다 — "최종 reply/report만 완료" 규약과 동일.
  - 세션 사망 = 끊긴 연결의 잠금이 풀리듯 hold도 풀린다. 어댑터가 발신자에게 failed report를
    대신 보내는 규약(2026-09-04)이 롤백에 해당한다.
  - 잠금은 작업(correlation_id)마다 잡히고, 바인딩은 열린 작업이 하나라도 있는 동안 잠긴다.
  - 기간 없음. 세션 생존만 하트비트로 확인한다. 살아 있는데 회신하지 않는 세션은 잠금이 풀리지
    않는다(긴 트랜잭션) — 소유자가 CLI로 강제 해제하는 수단을 둔다(DB의 세션 강제 종료에 해당).
- 구현(2026-09-09): 세션은 `become`으로 바인딩을 여럿 쥘 수 있고, 도구에 `binding` 인자로 고른다
  (하나만 쥐었으면 생략). 밀려난 세션은 `notifications/brevduva/evicted`를 받는다. 잠긴 바인딩의
  `become`은 거부되고 어떤 작업이 잡고 있는지 알려 준다. NATIVE_SESSION_DELIVERY.md의 단일
  바인딩 고정은 **번복**됐다.
- **깨어난 세션의 정체성 증명 — 회귀 수정(2026-09-11)**: 브리지는 `BREVDUVA_BINDING`·`BREVDUVA_WAKE`로
  정체성과 깨우기 창의 잠금을 대신 세운다. 그런데 MCP 자식에 환경변수를 넘기지 않는 러너(Codex —
  2026-09-04 실측)에서는 그 값이 브리지에 닿지 않아, 깨어난 세션이 `wake` 없이 `become`하다 자기 창의
  잠금에 막혔다. 6단계 브리지 전환 때 옛 상태 파일 폴백이 레거시 경로에만 남아 생긴 회귀다(무인 Codex
  답신 불능). 수정: 리시버가 발급한 깨우기 식별자를 **프롬프트에** 싣고 세션이 `become(wake=…)`으로
  넘긴다 — 모든 러너가 확실히 전달하는 통로이고, 리시버가 자기 기록과 대조하므로 동료 메시지가 지어낼
  수 없다. 환경변수 경로는 넘겨주는 러너(Claude)를 위해 그대로 둔다. 같은 프롬프트의 폴링 지시
  (`wait_for_message`)는 평면에 없는 도구라 뺐다.

### P8. 갱신은 서비스 한 곳에 닿으면 끝난다

- 설치기는 서비스를 서비스 관리자(SCM·systemd·launchd)로 재기동하고, 서비스가 실행하는 파일을
  새 바이너리로 맞춘다(2026-09-04 결정 유지). 세션 어댑터는 얇아서 갱신 대상이 아니거나, 서비스와
  버전 악수를 해서 옛 어댑터가 서버와 대화하는 일이 없다.
- 갱신 잔재(`.old` 등)는 서비스가 기동 시 스스로 치운다. 설치 위치는 하나다.
- 근거: Windows는 실행 중 exe를 덮어쓸 수 없어 옛 파일을 비켜 두고, macOS·Linux는 덮어써도 뜬
  프로세스가 옛 inode를 계속 쓴다. 세 OS 모두 "이미 뜬 어댑터는 옛 코드"다. 러너가 띄운 어댑터의
  수명은 러너가 쥐고 있어 설치기가 재기동할 수 없다.
- 구현(2026-09-09, 일부): 브리지가 기동 시 리시버 버전과 자기 버전을 대조해 다르면 이유를 말하고
  물러난다 — 옛 어댑터가 조용히 옛 규약으로 도는 일이 없다.
  **진행(2026-09-11, 7e)**: 이전 리시버의 Desktop 작업 연결 worker는 연결 의도 파일이 사라지면 스스로
  끝나므로, 리시버가 기동할 때 그 파일을 지워 옛 worker를 멈춘다(종전 설치기의 `brv connection restart`
  단계는 삭제). 옛 어댑터 기록은 지우지 않고 끝나지 않은 항목을 로그로 알린다 — 옛 경로는 기록 즉시
  서버에 확정했기 때문이다. **완료(2026-09-12, 10단계)**: ① 갱신이 비켜 둔 옛 실행 파일(`brv.old`·
  `brv.exe.old`·`brv.exe.old.<id>`)은 리시버가 기동할 때와 `brv daemon restart`(설치기가 부른다) 때 그 실행 파일 옆에서
  치운다 — 옛 프로세스가 아직 쓰면 지우지 못하고 다음 기회에 다시 한다 ② 브리지는 버전 대조를 기동 때 한 번에서
  **요청마다**로 넓혔다 — 모든 요청에 자기 버전을 싣고, 리시버는 다르면 409와 "이 앱의 MCP를 재시작하라"는 이유로
  거부한다(헤더 없는 직접 HTTP 클라이언트는 그대로 받는다). 갱신 전부터 러너 안에 떠 있던 브리지가 새 리시버와 옛
  규약으로 대화하지 않는다 ③ 재구축 이전의 옛 `brv mcp`(서버에 직접 JOIN)는 리시버에 붙지 않으므로 리시버가 막을 수
  없다 — 그것이 채널 자리를 가져가면 리시버는 standby가 되고, `brv status`가 그 가능성과 조치(그 앱의 MCP 재시작)를
  보인다. 설치기의 마지막 안내(앱마다 MCP 재시작)는 유지한다 ④ 이전 리시버 기록의 끝나지 않은 항목은 기동 로그와
  `brv status`가 같은 판정으로 보인다.
  **보강(2026-09-13, 0.7.1)**: 갱신은 **러너 쪽 등록**에도 닿아야 한다 — 등록은 `{brv} mcp --config … --host …`
  인자를 러너 설정에 박아 두므로, 인자 형식이나 실행 파일 경로가 바뀐 갱신 뒤에는 옛 인자로 중계기가 뜬다.
  0.7.0 갱신 직후 실사고: Codex가 옛 `--binding` 등록으로 중계기를 띄웠고 중계기가 거부하자 Codex는 stderr를
  삼켜 "MCP startup failed … initialize response"만 보였다 — 사용자에게는 **업데이트마다 반복되는 고장**이다.
  ⑤ 설치기가 부르는 `brv daemon restart`가 설정 옆 표시 파일(`mcp-registered.version`)이 지금 버전이 아니면
  탐지된 러너 전부에 등록을 다시 쓴다(Claude는 지우고 등록, Codex는 `mcp add`가 덮어씀 — 실측). 등록 명령이 없는
  러너는 종전처럼 붙여 넣을 조각을 보인다. 이 뒤처리는 서비스 유무와 무관하게 돈다 ⑥ **번복**: 옛 `--binding`이
  남은 등록을 중계기가 거부하던 것을 **무시하고 붙는 것**으로 바꿨다 — 낡은 것은 러너 설정의 인자뿐이고 중계기
  자체는 지금 버전이므로 거부는 사용자만 멈춘다(정체성은 여전히 `become`). stderr에 경고만 남긴다.
  ⑦ 자동 등록의 "바인딩이 여럿이면 안내만"(페이즈 27) 가지는 삭제 — `brv mcp`는 바인딩을 고르지 않는다.

### P9. 위 원칙은 세 OS에 동일하게 적용한다

- OS별 예외는 이 문서에 적힌 것만 허용한다. 현재 적힌 예외: Windows 서비스 계정(LocalSystem +
  깨우기·러너 입력 전달은 로그온 사용자 명의 — P5의 2026-09-10 실측), 토큰 저장 위치(맥 서명 빌드만
  키체인, 나머지 파일), **macOS는 LaunchAgent(로그인 후 기동)로 유지**(2026-09-09 U4 비교 결과 — 아래).
- macOS 기동 시점 비교: LaunchDaemon은 부팅 시 루트로 뜨지만 sudo 설치, 루트→사용자 깨우기
  (winspawn 상당을 새로 구현), 키체인 불가(서명 빌드 토큰을 파일로 전환)를 요구한다. 결정적으로
  FileVault가 켜진 Mac은 사용자가 로그인해 디스크 잠금을 풀기 전에는 LaunchDaemon도 뜨지 못해
  "로그인 전 수신"이 실제로 생기지 않는다. 비용 대비 이득이 없어 LaunchAgent를 유지하고, 로그인
  전 메시지는 서버 큐가 보관한다.
- 실기 검증도 세 OS에서 한다. "CI 통과"는 해당 OS 실기 성공이 아니다(기존 문서 규율 유지).

## 3. 러너·전달 능력 표기

러너마다 세 칸을 실측 여부와 함께 표시한다: **무인 깨우기 / CLI 유인 밀어넣기 / GUI 유인
밀어넣기**. `brv status`와 문서가 같은 표를 쓴다. 0.6.39의 `attended: turn-end hook` 표기는
Stop 훅(턴 종료 시 pull)만 보여 Monitor push 경로를 가렸다 — 표기 체계 자체를 바꾼다.
