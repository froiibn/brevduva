# 리시버의 세션 전달 설계 — 2026-09-05

상태: 해결 구조와 Codex 전달 인터페이스 실측. **제품 구현·배포 완료가 아니다.**

목표는 두 가지를 함께 만족하는 것이다.

1. 사람이 요청을 보냈던 작업 세션이 늦은 답신을 받고 그 문맥에서 계속 일한다.
2. 사람이 떠나 있어도 무인 작업이 같은 문맥에서 이어진다.

## 기존 전제의 수정

MCP 서버가 임의로 호스트의 턴을 시작할 수 없다는 것과, 러너에 외부 제어 API가 없다는 것은 다른 주장이다.

Codex app-server에는 `thread/resume`, `turn/start`, `turn/steer`가 있다.
로컬 codex-cli **0.153.3**이 생성한 JSON Schema에서도 세 메서드를 확인했다.
공식 문서: <https://learn.chatgpt.com/docs/app-server>.

`scripts/probe_codex_session_delivery.py`로 실제 app-server를 실행해 다음을 확인했다.

| 실측 | 결과 |
|---|---|
| 첫 턴이 완료된 같은 thread에 늦은 입력을 전달 | 성공, 다음 모델 요청에 원래 입력이 남음 |
| app-server 종료 후 새 프로세스에서 정확한 thread ID로 resume | 성공, 이전 두 입력이 모델 요청에 남음 |
| 진행 중인 턴에 expectedTurnId를 지정해 steer | 성공, 같은 turn ID로 수락 |
| steer로 보낸 입력의 문맥 보존 | 성공, 뒤의 모델 요청에서 확인 |
| 같은 app-server에 붙은 다른 클라이언트의 완료 이벤트 수신 | 성공, dispatcher가 시작한 동일 turn ID 관찰 |
| 관찰 클라이언트에서 전달된 입력의 이력 조회 | 성공, 동일 thread에서 입력 확인 |

테스트는 별도의 임시 CODEX_HOME·작업 폴더·로컬 모의 Responses 서버를 사용한다.
실제 계정, 사용자 작업 세션, Brevduva 서버, 외부 모델을 사용하지 않는다.
확인한 것은 **실제 러너의 입력 전달·이력 보존**이며 모델의 작업 수행 능력이나 답신 도구 호출 성공이 아니다.

```powershell
python scripts/probe_codex_session_delivery.py <codex.exe의-절대경로>
```

프로브가 출력하는 `state_directory`에 격리된 세션 기록과 stderr 로그가 남는다.
기존 CODEX_HOME은 수정하지 않는다. Python 표준 라이브러리와 Node.js 22 이상이 필요하다.
Node 내장 WebSocket을 공유 서버 연결에 사용하며 추가 패키지는 설치하지 않는다.

### 아직 증명하지 않은 것

- 별도로 실행한 app-server가 기존 Codex Desktop/TUI의 **라이브 실행체**를 제어할 수 있다는 보장은 없다.
- 같은 thread ID를 두 프로세스가 각각 resume하는 것은 라이브 세션에 attach하는 것과 다르다.
  프로브의 재개 시험은 기존 프로세스를 종료한 뒤 수행했다.
- Windows 0.153.3의 `app-server daemon version`은 daemon lifecycle이 Unix 전용이라고 반환했다.
  기존 GUI 세션에 연결할 수 있다는 근거로 Unix 관리 명령을 사용할 수 없다.
- 공유 app-server의 두 프로토콜 클라이언트 간 이벤트 전달은 확인했다.
  실제 제품 UI 표시·승인 처리·재접속 E2E는 별도 검증해야 한다.
- Claude Code와 다른 러너의 기존 실행체 전달 경로는 이번 실측에 포함되지 않는다.

따라서 기존 RunnerSpec의 `attended`를 Codex 전체에 대해 `direct`로 승격하지 않는다.
지원 능력은 러너 이름 하나가 아니라 **실제로 연결한 endpoint**에 귀속되어야 한다.

## 근본 원인과 결정

현재 `brv mcp`의 idle park는 60초 뒤 서버의 접속 자리를 반납한다.
데몬은 빈 자리를 되찾아 메시지를 받고 `spawn_wake`로 새 실행체를 만든다.
접속 자리의 소유자가 바뀌는 것이 요청을 보낸 작업 문맥의 소유자까지 바꾸고 있다.

**접속 소유권과 작업 소유권을 분리한다.**

- 에이전트 정체성: 기존 `(server, org, agent, channel)`. 공개 주소·토큰·큐의 의미는 유지한다.
- 작업 세션: 요청·답신·문맥이 귀속되는 안정적인 `work_session_id`.
- 실행 endpoint: 지금 작업 세션을 실행할 수 있는 러너, host, vendor thread ID, 제어 연결.
- 실행 임대: 같은 작업 세션을 동시에 실행하지 못하도록 하는 단일 소유권과 세대 번호.

소켓이 끊겨도 작업 소유권은 사라지지 않는다. 임대가 만료돼도 답신을 다른 작업 세션에 자동 이전하지 않는다.

## 전달 규칙

```text
도착한 메시지
  → 작업 세션 결정
      correlation 응답: 원래 요청을 발행한 작업 세션
      새로운 요청: 바인딩에 명시적으로 지정한 기본 작업 세션
  → 해당 작업 세션의 보관함에 영속 저장
  → 실행 임대 확인
      살아 있는 endpoint: 같은 러너 세션에 전달
      실행체가 종료됨 + 재개 가능: 같은 문맥을 resume하고 전달
      재개 불가 또는 전달 불명확: 보관하고 상태·사람에게 알림
  → 입력 수락 / 실행 중 / 완료 / 실패를 구분해 기록
```

correlation은 `reply`뿐 아니라 해당 요청의 `ack`와 `report`에도 적용한다.
새 메시지는 기본 세션으로 보낼 수 있지만, 이미 소유자가 정해진 요청의 답신은
기본 세션 변경이나 접속 시각에 따라 재배정하면 안 된다.
소유자를 알 수 없는 과거 correlation을 특정 세션의 것이라고 추정하지 않는다.

사람의 작업 세션과 무인 작업 세션을 항상 분리할 필요는 없다.
같은 `work_session_id`를 사람이 보고 작업하다가, 이후 실행 임대만 무인 실행기가 이어받는다.
사람이 돌아오면 같은 세션의 진행 내용과 결과를 본다.

### 서버와 로컬 리시버의 경계

로컬 lease만으로는 다른 머신·모바일에서 시작한 요청의 소유자를 알 수 없다.
**전체 제품 해법에는 서버의 작업 소유권과 세션별 보관함이 필요하다.**
서버는 인증된 요청 발행 경로에서 소유권을 확정하고 보관함별 접근 권한을 검사해야 한다.
메시지 payload에 적힌 session ID나 임의의 원격 메타데이터를 실행 권한으로 신뢰하지 않는다.

이것은 현행 프로토콜 2.2의 '에이전트에 큐 귀속·동시 활성 접속 하나' 위에
새 전달 의미를 더하는 작업이다. 서버/공유 스키마를 변경하기 전에
PROTOCOL.md 및 영문판에서 보관함, 등록, 소비, 재전달 규칙을 먼저 확정해야 한다.
구체적인 서버 저장 기술은 공개 리시버 설계에 포함하지 않는다.

## 러너 어댑터의 계약

```text
inspect(endpoint) → absent | idle | active(turn_id) | needs_attention
deliver(endpoint, delivery_id, payload, expected_generation)
  → accepted(receipt) | rejected(reason) | unknown
resume(work_session, expected_generation) → endpoint | unavailable
reconcile(delivery_id, endpoint) → accepted(receipt) | absent | unknown
```

Codex에서 idle은 `turn/start`, active는 `turn/steer(expectedTurnId)`로 매핑할 수 있다.
턴 종료와 steer 사이의 경합은 상태를 다시 읽어 처리한다.
전달 실패를 이유로 다른 thread를 만들거나 `exec --last`로 최근 작업을 골라서는 안 된다.
재개는 명시적으로 기록한 ID로만 수행한다.

진행 중인 작업에 모든 메시지를 즉시 섞는 것은 별도 정책이다.
관련 correlation 응답은 진행 중인 턴에 전달할 수 있다.
독립된 새 요청은 같은 작업 세션의 다음 턴으로 대기시키는 것을 기본으로 한다.
사용자 취소·승인 대기·중단 상태도 단순 idle로 처리하지 않는다.

권한은 기존 러너·작업 세션의 로컬 정책을 유지한다.
원격 메시지로 작업 폴더, 모델, 샌드박스, 승인 정책을 변경하지 않는다.
사람이 필요한 승인은 `needs_attention`으로 드러낸다. 무인 모드를 이유로 자동 우회하지 않는다.

## 소비와 실패 처리

현행 daemon의 스폰 성공 ACK를 이 경로에 그대로 적용하면 안 된다.
안전한 경계는 **메시지를 다시 찾을 수 있는 영속 보관함으로의 인계**다.

1. 원래 메시지 ID를 포함해 세션 보관함에 중복 없이 저장한다.
2. 보관 성공 후 transport ACK를 보낸다. ACK는 작업 완료를 뜻하지 않는다.
3. dispatcher가 저장된 건을 러너에 제출한다.
4. 러너가 수락하면 thread/turn/item 식별자와 수락 상태를 저장한다.
5. 완료·실패는 별도로 저장하고 원래 요청자와 사람이 보던 세션에 표시한다.

프로세스가 메시지를 받기 전, 받는 도중, 수락 응답을 보낸 직후 죽는 창을 구분해야 한다.
API 요청이 timeout됐다는 이유로 새 턴을 바로 만들면 중복 실행될 수 있다.
이 경우는 `unknown`으로 남겨 세션 이력을 조회해 수락 여부를 대조한다.
결론을 낼 수 없으면 자동 재실행하지 않고 주의가 필요한 상태로 남긴다.

현재 Codex 스키마의 `clientUserMessageId` 필드 존재만으로 exactly-once 또는
중복 억제를 보장한다고 가정하지 않는다. 이 필드의 재시도 의미는 추가 실측 대상이다.
응답이 모호한 상황에서도 안전하게 재시도할 수 있어야 운영 경로로 승격한다.

## 구현 순서와 통과 기준

### 1. 공유 런타임의 세션 전달 E2E

- 리시버와 사람의 UI가 **같은 app-server 실행체**에 연결된다.
- 사람이 세션 A에서 요청 → 턴 종료 → 60초 이후 답 도착 → A에서 새 턴 시작 및 UI 표시.
- A가 실행 중일 때 관련 답신이 도착하면 같은 턴으로 들어가고 사용자 작업이 중복 실행되지 않는다.
- 승인 대기와 사용자 취소를 존중한다.

현재 완료한 프로브는 이 단계의 **러너 API/문맥 보존 부분**이다.
기존 Desktop/TUI 연결 및 Brevduva 왕복 E2E는 미완료다.

### 2. 작업 소유권·영속 보관함

- 발행 직후 빠른 답신이 와도 소유권 등록보다 먼저 소비되지 않는다.
- 같은 에이전트의 다른 세션 B가 접속해도 A의 correlation 응답은 A에 남는다.
- 리시버가 재시작돼도 pending·accepted·unknown 상태를 복원한다.
- 동일 메시지 재전달을 중복 작업으로 만들지 않는다.

### 3. 무인 인계와 재개

- A의 실행체를 종료하고 같은 ID로 재개했을 때 기존 문맥과 미처리 입력을 이어받는다.
- 살아 있는 실행체와 재개 실행체가 동시에 실행되지 않도록 임대 세대 번호로 차단한다.
- 재개 불가·인증 실패·승인 필요 시 보관하고 이유를 표시한다.
- 전달 endpoint가 없는 러너는 알림·poll·검증된 훅 경로를 사용하며 즉시 전달을 주장하지 않는다.

### 4. 단절·테이크오버 창

새 세션 전달과 별도로, 단절 중 잡혀 있던 미확인 메시지의 신속한 재전달을 검증한다.
타이머를 조정하는 것만으로 작업 세션 소유권이나 문맥 문제가 해결되지는 않는다.

## 채택하지 않는 우회

- 60초 idle 시간을 길게 늘려 소유권을 우연히 유지하기
- 모델에게 영구 대기 루프를 돌도록 지시하기
- `--last`로 가장 최근 세션을 선택하기
- 같은 vendor thread를 여러 프로세스에서 동시에 resume하기
- 전달이 실패하면 새 headless 세션으로 답신을 넘기기

이들은 지연이나 실행 빈도를 바꿀 수 있지만, 답신을 원래 작업 문맥에 돌려준다는 조건을 보장하지 않는다.
